# 面试亮点：Agent 任务失败的重试与容错设计

> **一句话亮点**：面对失败，不靠「祈祷它别挂」，而是先给失败**分类**（可重试 / 不可重试），再上一整条**防御链**（调用级退避重试 → 任务级重规划 → 确定性兜底 → 人机确认 → 可观测），让每一次失败都**可救、可控、可追溯**。

---

## 一、问题背景

Agent 系统里失败无处不在，且分两个层次：

| 层次 | 典型失败 | 本项目位置 |
|---|---|---|
| **微观 · LLM 调用** | 限流 429、超时、连接抖动、JSON 解析失败 | `llm.invoke()` / `_extract_json_array` |
| **宏观 · 任务执行** | 子任务报错、计划结构非法、工具连续失败、死循环 | `executor_node` / `planner_node` / `replan_node` |

**本项目的现状**：
- planner 生成计划会**结构化校验 + 回喂重试**（`MAX_PLAN_RETRIES = 3`），最终**确定性兜底**（`_default_plan`）；
- 子任务失败由 `replan_node` **局部重规划**（`MAX_REPLAN = 2`），成功后解锁下游；
- 但 `executor_node` 目前是 `except Exception` **一刀切**——一个 503 抖动和一个「逻辑写错」被同等对待，都会触发一次昂贵的 replan。

**核心矛盾**：失败是**必然**的，但「值不值得救 / 怎么救」每个失败都不一样——**分类错了，重试就是白烧钱**。

---

## 二、问题根源：失败要先分类

最关键的一条认知：**不是所有失败都该重试。**

| 类型 | 例子 | 特征 | 正确处理 |
|---|---|---|---|
| **瞬时故障（transient）** | 429 限流、503、超时、网络抖动 | 重试**可能**成功 | **退避重试** |
| **确定性故障（deterministic）** | 400 参数错、校验失败、权限错、逻辑错 | 重试**一万次也一样** | **改**，不是**试** |

> **踩坑**：把「瞬时」当「确定性」→ 明明重试一下就好，却直接判失败去重规划，浪费一轮 LLM + 重跑；
> 反过来把「确定性」当「瞬时」→ 死循环重试，把预算烧光（本项目阶段 6 的防死循环就是防这个）。

其余失败根源：LLM 输出**非确定**（概率采样、语法无约束、长度截断、语义不可控）、工具是**外部依赖**（可能挂）、图是**循环结构**（可能不收敛）。

---

## 三、大厂的考虑

大厂不是「把重试次数调大」，背后是四层考量：

1. **用户体验底线**：要的是「**永远有个结果**」，不是「永远正确」。一次硬失败比一个略差但可用的结果更伤体验。
2. **成本意识**：每次重试都是钱和时间。能「修复」就不「重问」，能「降级」就不「重试」——**逐层找更便宜的退路**。
3. **把 LLM 当不稳定下游服务**：直接复用分布式系统那套容错（重试 / 退避 / 熔断 / 隔离 / 降级），Java 里 Hystrix / Resilience4j / Sentinel 干的就是这个。
4. **失败要「安全」**：不只是重试，还要**幂等**（重试不产生重复副作用）、**可观测**（失败率面板）、**有预算**（错误预算 error budget）。

心智模型：**先分类 → 值得救就用退避重试救 → 救不动才降级 / 重排 / 挂起 / 进死信 → 全程可观测有预算。**

---

## 四、大厂的解决方案：三层防御链

### 第 0 层 · 错误分类（最重要）
区分 transient / deterministic，决定走「重试」还是走「改」。**没有这一步，后面全是错的。**

### 第 1 层 · 调用级（微观，网络 / API 调用）

| 手段 | 说明 | 本项目 |
|---|---|---|
| 指数退避 + 抖动 | 1s→2s→4s，再乘随机抖动，防「惊群」 | 缺 |
| 超时 | 每次调用设 deadline，别无限等 | 缺 |
| 熔断器 | 连续失败就「跳闸」，别再打下游 | 缺 |
| 隔离舱 | 不同依赖用不同线程池，一个拖垮不了一片 | 缺 |
| 模型 fallback | 主模型挂了切备用模型 | 缺 |

### 第 2 层 · 任务级（宏观，LangGraph 图）

| 手段 | 说明 | 本项目 |
|---|---|---|
| 结构化输出回喂重试 | 校验不过 → 把错误喂回去改 | ✅ `planner_node` |
| 确定性兜底 | LLM 彻底不行就用固定模板 | ✅ `_default_plan` |
| 局部重规划 | 只返工失败的那一步，保留成功部分 | ✅ `replan_node` |
| 幂等性 | 重试不产生重复副作用 | ✅ 半有（成功才入库、按 id 记） |
| 持久化执行 / 检查点 | 每步落盘，宕机从中断点恢复（Temporal / Cadence） | ✅ 阶段 2 Checkpointer |
| 人机确认（HITL） | 拿不准就 `interrupt()` 挂起让人拍板 | ⏳ 阶段 6 |
| 可观测 + 错误预算 | 失败率面板、SLO、告警（Google SRE） | ⏳ 阶段 8 |
| 死信队列 + 补偿 | 彻底失败进 DLQ，定时 / 人工兜底（Saga） | 缺 |

### 第 3 层 · LLM 特有的自我修复
**Reflexion / 自我修正**（把错误回灌让模型自己改）、**语义去重**（别重复调同一工具，见阶段 6 anti_loop）、**token / 工具调用预算**（超预算直接停）、**换采样**（重试时换 seed 或换模型）。

## 五、重试次数到底怎么定（面试高频）

**先说结论**：本项目 `MAX_PLAN_RETRIES=3`、`MAX_REPLAN=2`、`MAX_STEPS=8`、`iteration_count` 上限 5，**都是启发式默认值，没有实测依据**——先够用、别失控。真正的定法分三步：

**1. 定指标**：成功率、P99 延迟、单任务成本（阶段 8 evaluation 干这个）。

**2. 算收益**：`N 次重试的总成功率 ≈ 1 - (1-p)^(N+1)`

| 单次成功率 p | 0 次重试 | 1 次 | 2 次 | 3 次 |
|---|---|---|---|---|
| 0.7 | 0.70 | 0.91 | 0.97 | 0.99 |
| 0.9 | 0.90 | 0.99 | 0.999 | ~1.0 |

> p=0.7 时，到第 3 次边际收益已经很小，成本却在涨——**这就是「3 而非 10」的数学依据**。

**3. 设护栏**：重试必须有**总预算**（总时间 / token / 次数），否则一个坏任务能把配额烧光。

**各参数为什么这么给**：
- `MAX_PLAN_RETRIES=3`：**纠正性重试**（带错误回喂），通常 1~2 次收敛；第 3 次再不行多半是系统性理解错，多喂白搭。
- `MAX_REPLAN=2`：重规划**贵得多**（一轮 LLM + 重跑子任务），且很多失败不是「换个排法」能救，所以给得比 plan 重试少。
- `MAX_STEPS=8`：控制**爆炸半径**，长链失败概率按 `(1-p)^n` 累积。
- 防死循环用 `replan_count` 封顶，超限就**放弃并收尾**，绝不无限打转。

## 六、本项目落地：已有 / 缺口

**已具备**（可现场指代码）：
- 结构化输出「生成 → 校验 → 回喂重试 → 确定性兜底」闭环（`plan_graph.py`）
- 局部重规划只返工失败子任务（`replan_node`）
- 多重上限防失控：`MAX_PLAN_RETRIES` / `MAX_REPLAN` / `MAX_STEPS`
- 幂等沉淀：成功才写 `subtask_results`

**最该补的三处（和大厂差距最大）**：
1. **错误分类 + 调用级退避重试**：`executor_node` 里区分「瞬时 → 退避重试 2~3 次」和「语义失败 → 才交 replan」。
2. **重试总预算**：给整条流水线一个总 LLM 调用 / 总耗时上限，而非每处各自重试。
3. **超时 + 熔断**：至少给 LLM 调用加超时，防一个卡死请求拖住整图。

## 七、面试话术（可直接说）

> 「Agent 里的失败是必然的，我的做法是**先分类、再上防御链**。第一原则是把失败分成**可重试**（限流、超时这类瞬时故障）和**不可重试**（参数错、校验失败这类确定性故障）——前者退避重试、后者必须改而不是试。防御链分三层：调用级做超时、指数退避加抖动、熔断和模型 fallback；任务级做结构化输出回喂重试、局部重规划、确定性兜底；LLM 特有的是把错误回灌让它自我修正、做语义去重防重复调用。重试次数不是拍的，是用 `1-(1-p)^(N+1)` 算边际收益，再设总预算封顶——比如单次成功率 0.7 时到第 3 次收益就很小了。本质上是把分布式系统里『重试、熔断、降级、兜底』那套容错思想，平移到了 LLM 这个不稳定组件上，而且让失败可观测、有预算、可恢复。」

## 八、可能的追问与应对

| 追问 | 应对 |
|---|---|
| 「重试次数为什么要封顶，多试几次不好吗？」 | ① 收益递减：`1-(1-p)^(N+1)` 很快饱和；② 成本线性涨；③ 确定性故障重试无效；④ 不封顶会掩盖系统性问题（一直重试说明 prompt / 架构有 bug）。 |
| 「瞬时错误和语义错误在代码里怎么区分？」 | 按异常类型 / HTTP 状态码 / 错误信息分类：`429/5xx/Timeout` → 可重试；`ValidationError/4xx/业务错` → 不可重试。工程上用一张「异常 → 策略」映射表。 |
| 「怎么防重试风暴（惊群）？」 | 指数退避 + **随机抖动**（否则一齐重试打垮下游）+ 熔断器 + 服务端重试预算 / 令牌桶。 |
| 「重试会不会产生重复副作用？」 | 必须先保证**幂等**：写操作带幂等键（如 Stripe 的 idempotency key），或先查后写、按 id 去重。本项目子任务按 id 记录、成功才入库就是这个思路。 |
| 「LLM 任务失败，为什么不用『让用户重试』解决？」 | 把不确定性转嫁给用户伤体验。系统应自己消化可恢复的失败，只有真正拿不准的关键决策才打断用户（HITL）。 |
| 「你怎么知道自己的重试参数是合理的？」 | 不靠拍脑袋——用阶段 8 的评估体系测成功率 / P99 延迟 / 单任务成本，再用数据回归调参；参数只是初始值，靠 benchmark 收敛。 |
