# 面试亮点：LLM 结构化输出的容错与降级设计

> **一句话亮点**：面对大模型输出的不确定性，不靠「让它别错」，而是默认它会错，用「重试 → 修复 → 降级 → 确定性兜底」的容错链，保证任务**永不整体失败**。

---

## 一、问题背景

在 Agent 系统里，经常需要让大模型输出**结构化数据**而不是自由文本，例如：

| 场景 | 需要的结构化输出 |
|---|---|
| 任务规划（Plan-and-Execute） | 把复杂任务拆成带依赖关系的子任务列表（JSON 数组） |
| 工具调用（Function Calling） | 输出 `{tool_name, args}` 结构化参数 |
| 信息抽取 | 从文档抽 `{实体, 关系}` 三元组 |

**本项目典型场景**（`graph/plan_graph.py`）：Plan-and-Execute 模式中，planner 节点需要生成计划：

```json
[
  {"id": "1", "desc": "查资料", "agent": "knowledge", "deps": []},
  {"id": "2", "desc": "写代码", "agent": "code", "deps": ["1"]},
  {"id": "3", "desc": "写报告", "agent": "writer", "deps": ["2"]}
]
```

后续 dispatcher 节点要按这个计划的依赖关系**拓扑排序、派发子任务**。如果这个 JSON 结构坏了（字段缺失 / 依赖成环 / agent 名非法），整条复杂任务流程就走不下去。

**核心矛盾**：下游强依赖「结构正确」，而 LLM 偏偏「结构没保证」——这就是容错设计的出发点。

---

## 二、问题出现的原因

大模型输出本质上是**非确定**的，有四个根源：

1. **概率采样**：模型逐 token 生成，每一步按概率分布采样，同一个输入可能得到不同输出（哪怕 `temperature=0` 也不能彻底消除）。
2. **语法无约束**：自由文本生成时模型想怎么措辞都行——可能给 JSON 套 markdown 围栏、加解释文字、少个右括号、把双引号写成单引号。
3. **长度截断**：生成到一半撞上 `max_tokens` 上限直接截断，输出半个 JSON。
4. **语义不受控**：即便结构对了，字段的**值**也可能错（比如 `agent` 填了个不在白名单里的名字）。

> **关键认知**：结构（形状）可以被「约束」，内容（语义）只能靠「校验」。没有任何手段能保证语义正确——这也是为什么「结构化输出」不等于「结果可靠」。

---

## 三、大厂的考虑

大厂不会让单点 LLM 失败导致整个任务失败，背后的考量有四条：

1. **用户体验底线**：用户要的是「**永远有个结果**」，不是「永远正确」。一次硬失败（报错 / 卡死）比一个略差但可用的结果更伤体验。
2. **成本意识**：重新调一次 LLM 既慢又花钱。能「修复」就不「重问」，能「降级」就不「重试」，每一层都追求更便宜的退路。
3. **工程成熟度**：把 LLM 当成「**可能挂掉的下游服务**」对待，直接复用分布式系统那套容错手段（重试 / 熔断 / 降级 / 兜底）——Java 里 Hystrix / Sentinel 干的就是这个。
4. **可观测性**：记录失败率与失败原因，用数据决定「调 prompt、降级、还是换模型」，而不是拍脑袋。

---

## 四、大厂的解决方案

核心是「**逐级降级到确定性兜底**」，一条四层容错链：

| 层 | 手段 | 解决什么 |
|---|---|---|
| ① 重试 + 退避 / 换模型 | 失败重试、指数退避、超时切换备用模型 | 瞬时故障（超时 / 限流 / 偶发坏输出） |
| ② 修复而非重问 | 用 `json5` / `json-repair` 修坏 JSON、正则抽取关键字段 | 格式坏了但内容还在 |
| ③ 降级到确定性兜底 | **不靠 LLM**，用规则 / 模板产出结果 | LLM 彻底不配合 |
| ④ 失败隔离到子任务 | 局部重规划，保留已成功部分 | 一步失败拖垮全局 |

> **关键在第 ③ 层**：容错链的尽头，一定有一个「不依赖 LLM、100% 能产出」的确定性方案。这样最坏情况任务也不全挂，只是质量下降。这是「能上线」和「demo」的分水岭。

### 本项目落地（对应代码，可现场指给面试官看）

| 容错层 | 本项目实现 |
|---|---|
| 提示词约束（①的铺垫） | `_build_plan_prompt`：明确要求只输出 JSON 数组 + 5 条规则 |
| 容错解析（②） | `_extract_json_array`：剥掉 markdown 围栏 → 定位 `[ ... ]` → `json.loads` |
| 语义校验 + 重试（① + ②） | `_validate_plan`：校验步骤数 / id 唯一 / agent 白名单 / 依赖无环（Kahn 拓扑排序）；失败把错误回喂 LLM 重试（最多 3 次） |
| 确定性兜底（③） | `_default_plan`：重试耗尽后返回固定三步线性计划，**不再抛异常**，任务继续推进 |

关键代码（降级不失败）：

```python
def _default_plan(user_input: str) -> list[dict]:
    """确定性兜底：LLM 规划彻底失败时，用固定三步线性计划。"""
    return [
        {"id": "1", "desc": "检索任务相关的课件/资料", "agent": "knowledge", "deps": [], "status": "pending"},
        {"id": "2", "desc": f"执行核心任务：{user_input}", "agent": "code", "deps": ["1"], "status": "pending"},
        {"id": "3", "desc": "汇总产出最终结果", "agent": "writer", "deps": ["2"], "status": "pending"},
```

## 五、面试话术（可直接说）

> 「LLM 输出是不确定的，尤其让它生成 JSON 这种结构化数据时，可能少括号、套 markdown 围栏、甚至语义出错。我的做法不是去赌它不出错，而是默认它会错，搭一条四级容错链：提示词约束 → 容错解析 → 语义校验 + 重试 → 降级到确定性模板。核心是最后一级——无论如何都有一个不依赖 LLM 的兜底，保证任务永不整体失败，最坏情况只是结果质量下降。这本质上是把分布式系统里『重试、熔断、降级、兜底』那套容错思想，平移到了 LLM 这个不稳定组件上。」

## 六、可能的追问与应对

| 追问 | 应对 |
|---|---|
| 「结构化输出（JSON Schema / Function Calling）不是能保证结构吗？为什么还要自己校验？」 | ① 它只保证「形状」不保证「值」（语义）；② 实践中仍有 max_tokens 截断、provider 实现差异等破绽；③ 所以校验 + 降级这层纵深防御无论如何都要有。 |
| 「降级到模板计划，质量变差怎么办？」 | 兜底是「底线」不是「常态」。正常路径 99% 走 LLM 的精细计划；兜底只保证那 1% 的失败也能给用户一个可用结果，且可通过可观测性数据持续压低失败率。 |
| 「为什么不直接让用户重试？」 | 让用户重试是把不确定性转嫁给用户，伤体验。系统应该自己消化掉可恢复的失败，只有真正拿不准的关键决策才打断用户（人机确认 HITL）。 |
