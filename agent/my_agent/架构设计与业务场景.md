# 大学生智能学习多Agent系统 — 架构设计与业务场景

> 基于 LangChain + LangGraph 的全场景学习辅助系统，覆盖课程答疑、习题解答、课件学习、代码实验、报告撰写、论文评审、错题复习。
>
> 本文档为**修正后的终稿**：修正了"三大范式严格解耦"的技术错误表述，补齐了 LLM 层容错、评估体系、上下文管理等原设计缺失环节，并给出每一步执行逻辑可能遇到的问题与应对技术。

## 一、项目概述

面向大学生全场景学习需求，基于 LangChain（能力封装）+ LangGraph（状态编排与多智能体调度）构建。

**技术栈**

| 层 | 技术 |

**核心亮点（修正版表述）**

## 二、架构定位与核心设计原则

### 2.1 LangChain 与 LangGraph 的分工（技术定位）

- **LangChain**：负责**能力封装** —— 工具封装、RAG、记忆、Skill、Prompt 模板、统一 LLM 调用。
- **LangGraph**：负责**编排调度** —— 状态管理、节点流转、分支路由、多 Agent 协作、循环控制、人机介入。

一句话：**LangChain 提供"零件"，LangGraph 负责"装配与运转"。**

### 2.2 范式分层（修正"三大范式解耦"的错误表述）

原设计将 ReAct、Plan-and-Execute、多Agent辩论并列称为"三大范式严格解耦"。**这是错误的**：

- ReAct 是**底层推理循环**（思考 → 调工具 → 观察 → 再思考）。
- Plan-and-Execute 与多Agent辩论是**上层编排模式**。
- 上层编排的每个 Agent 内部，仍然复用 ReAct 推理能力。

**正确表述为「1 底座 + 2 编排」：**

```
             ┌─────────────────────────────────────┐
             │        上层编排（2 种模式）            │
             │  Plan-and-Execute 流水线  │ 对等辩论    │
             └──────────────┬──────────────────────┘
                            │ 复用
             ┌──────────────▼──────────────────────┐
             │        底层推理（1 种范式）            │
             │             ReAct 循环               │
             └─────────────────────────────────────┘
```

答辩话术：**"一种底层推理范式（ReAct）+ 两种上层编排范式（规划流水线 / 对等辩论），上层编排复用底层 ReAct 推理，形成分层而非解耦的架构。"**

### 2.3 三大模式严格分工

| 模式 | 适用任务 | 编排方式 | 是否规划 | Agent 数量 |
|---|---|---|---|---|
| ReAct | 简单问答/单题计算 | 单 Agent 循环 | 无 | 1 |
| Plan-and-Execute | 复杂流程任务 | 顶层规划 + 流水线 | 有 | 多（分工） |
| 多Agent辩论 | 主观评审任务 | 对等博弈 | 无 | 多（对等） |

## 四、核心技术选型映射表（设计 → LangGraph 原语）

这张表是"业务设计"到"可写代码"之间的关键桥梁，答辩时可直接展示。

| 你的设计 | LangGraph 对应实现 |
|---|---|
| 任务复杂度分类器（路由层） | 入口 `classifier` 节点 + `add_conditional_edges` 按 `task_type` 分流 |
| 三张子图 | 三个独立 `StateGraph`，用父图 `add_node` 包装为 subgraph |
| ReAct 循环 | `agent` 节点 ↔ `tools` 节点，`add_conditional_edges` 判断继续/结束 |
| 防死循环 | 循环的 conditional edge 里加 guard 逻辑，或独立 `guard` 节点 |
| 工具人机确认 | 高危工具前 `interrupt()` 挂起，用户确认后 `Command(resume=...)` 恢复 |
| 短期记忆 | `Checkpointer`（`MemorySaver` / `SqliteSaver` 持久化 State） |
| 长期记忆 | 向量库存储历史经验摘要，检索相似经验 |
| 局部重规划 | 子任务失败 → 失败信息回填 planner 节点重跑，更新 plan list |
| 辩论消息池 | State 中 `messages: list` 字段，三 Agent 轮流 append，收敛条件写进 conditional edge |

**Java 类比**：LangGraph 的 `StateGraph` 是**状态机 + 工作流**，节点是方法，边是跳转条件；`interrupt()` 是工作流引擎里"需要人工审批的挂起点"；`Checkpointer` 是流程实例的持久化存储。

## 五、State 全局状态设计（具体 Schema）

所有节点共享的统一状态，是 LangGraph 的核心。下面是可直接落地的 TypedDict 定义：

```python
from typing import TypedDict, Annotated, List, Dict, Any
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    # 用户输入与任务分类
    user_input: str                      # 用户原始提问
    task_type: str                       # "simple" | "complex" | "debate"
    messages: Annotated[List[BaseMessage], add_messages]  # 对话消息（短期记忆）

    # 规划相关（complex 模式）
    plan: List[Dict[str, Any]]           # 任务计划列表 [{id, desc, agent, deps, status}]
    current_subtask_id: str              # 当前执行的子任务

    # 执行相关
    rag_results: List[str]               # RAG 检索结果
    tool_history: List[Dict[str, Any]]   # 工具调用历史 [{tool, args, result, ts}]
    iteration_count: int                 # ReAct 循环计数器
    final_output: str                    # 最终输出结果

    # 人机确认相关
    pending_tool_call: Dict[str, Any]    # 待用户确认的高危工具调用缓存

    # 辩论相关（debate 模式）
    debate_messages: List[Dict[str, str]] # 辩论消息池 [{role, content}]
    debate_round: int                    # 当前辩论轮次

    # 长期记忆
    long_term_index: List[str]           # 长期记忆检索索引
```

**设计要点**：
- `messages` 用 `add_messages` reducer，天然支持追加而非覆盖。
- 全局 schema 统一，三张子图只读写自己关心的字段，避免子图间状态不兼容。

## 七、能力模块设计

### 7.1 RAG 知识库系统（三层数据源）

| 优先级 | 数据源 | 内容 | 隔离性 |
|---|---|---|---|
| 高 | 用户私有上传库 | 课件、实验指导书、教材、往年试卷 | 个人独立向量库 |
| 中 | 个人学习沉淀库 | 历史代码、实验报告、错题、学习记录 | 系统自动沉淀 |
| 低 | 公共联网资源 | 兜底补充 | 公共 |

- 所有知识库读取**统一通过 MCP 协议**访问。
- 检索结果为空时：回退公共知识，并明确标注"未找到课件依据"，避免模型编造。

### 7.2 记忆系统

| 类型 | 内容 | 技术实现 |
|---|---|---|
| 短期记忆 | 本次会话上下文、任务进度、中间结果 | LangGraph `Checkpointer`（持久化 State） |
| 长期记忆 | 用户学科、薄弱点、历史任务经验、易错知识点 | 向量库存储经验摘要，按需检索 |

### 7.3 Skill 可插拔技能库（学生场景专属）

课件解析、习题推导、Verilog/Python 代码实验、报告生成、论文评审。
Agent 根据任务类型**动态加载**对应技能（技能 = 一段专用 Prompt + 一组专用工具 + 一套流程模板）。

### 7.4 工具安全分级

| 级别 | 工具示例 | 处理 |
|---|---|---|
| 安全工具 | RAG 检索、公式计算 | 自动执行 |
| 高危工具 | 代码运行、联网搜索、文件写入 | 必须用户确认后执行 |

## 八、安全与稳定性设计（两大难点落地）

### 8.1 防死循环模块（四层机制 + 实现方式）

| 机制 | 实现方式 |
|---|---|
| 1. 最大轮次硬限制 | `iteration_count >= 5` 强制结束，输出"已到最大轮次，基于已有信息作答" |
| 2. 重复工具参数检测 | 记录历史 `(tool_name, args_hash)`，相同则拒绝调用，提示模型换思路 |
| 3. 信息增益评估 | 由 LLM 判断"新结果相对已有信息是否带来新内容"，无新信息立即终止（工程实现为 LLM 判定，非严格信息论计算） |
| 4. 工具失败重试限制 | 同一工具连续失败 2 次自动停止，返回错误让模型换方案 |

> **诚实说明**：机制 3 是 LLM 判定的启发式方法，不是严格的信息论增益。答辩时明确说"信息增益由 LLM 判定 + 相似度去重实现"，避免被追问"增益怎么算"时卡壳。

### 8.2 工具安全人机确认模块（Human-in-the-loop）

高危工具调用流程：

```
Agent 生成调用参数
  → 安全拦截节点（判断工具级别）
  → 高危：interrupt() 挂起，展示调用详情给用户
  → 用户 同意 / 拒绝 / 修改参数
  → Command(resume=...) 恢复执行
```

彻底解决任意代码执行、隐私爬取、风险操作问题。

## 九、LLM 层容错设计（原设计缺失，必须补齐）

防死循环只解决了"循环"问题，但 LLM 层还有大量其他故障，实际运行天天遇到：

| 问题 | 应对技术 |
|---|---|
| 工具调用参数 JSON 解析失败 | 重试 + 容错解析（正则提取关键字段），仍失败则降级为不调工具 |
| 模型幻觉调用不存在的工具 | 工具名白名单校验，非法调用直接忽略并提示 |
| 模型幻觉编造答案（不检索） | 提示词强制"先检索后回答"，检索为空时明确说"不知道" |
| 上下文窗口溢出（长会话 + RAG） | 摘要压缩 / 滑动窗口裁剪历史消息 |
| 模型超时 / 限流 | 重试 + 指数退避 + 降级（切换备用模型） |

## 十、三大业务场景详细设计（核心）

> 每个场景给出：完整执行逻辑、**每一步可能遇到的问题**、**应对该问题的设计技术**。

### 场景一：简单任务 → ReAct 单 Agent 模式

**适用**：知识点解释、概念问答、单题计算、简单课件查询

**案例**：用户提问"解释计组中的流水线冒险，根据我上传的课件回答"

| 步骤 | 执行逻辑 | 可能的问题 | 设计的技术 |
|---|---|---|---|
| 1 | 用户提问 | 输入模糊/有歧义 | 路由 Agent 前置澄清或按默认理解处理 |
| 2 | 路由 Agent 分类为 simple | 复杂任务被误判为 simple | 分类器 LLM + 规则双保险，支持用户手动纠正 |
| 3 | 进入 ReAct 子图 | — | — |
| 4 | Agent 思考是否调工具 | 模型幻觉，不检索直接编答案 | 提示词强制"先检索后回答" |
| 5 | 调用 RAG 检索（安全工具自动放行） | 检索不到相关段落 | 结果为空时回退公共知识并标注"无课件依据" |
| 6 | 工具返回检索结果 | 结果与问题无关 | 相关性校验，不相关则换检索关键词 |
| 7 | Agent 再思考，判断信息充足 | 模型无限循环调工具 | 防死循环：轮次上限 + 参数去重 + 信息增益判断 |
| 8 | 整理答案输出 | 答案超出上下文窗口 | 摘要压缩历史消息 |
| 9 | 写入短期记忆，沉淀长期记忆 | — | Checkpointer + 向量库经验摘要 |

**模式特点**：无规划、无多 Agent、快速响应、自动防循环。

---

### 场景二：复杂流程任务 → Plan-and-Execute + 多 Agent 流水线

**适用**：课程实验、代码开发、完整实验报告、课程大作业、长流程多步骤任务

**案例**：用户上传 ALU 实验指导书，要求"完成 Verilog 代码编写、仿真调试、撰写完整实验报告、自查代码漏洞"

| 步骤 | 执行逻辑 | 可能的问题 | 设计的技术 |
|---|---|---|---|
| 1 | 路由分类为 complex | 误判 | 分类器双保险 + 用户纠正 |
| 2 | 进入 Plan 子图 | — | — |
| 3 | 规划 Agent 生成任务计划 | 规划不合理 / 步骤遗漏 | 结构校验（步骤数、依赖完整性），失败重新规划 |
| 4 | 按拓扑序分发子任务 | 子任务依赖错误 | 计划声明依赖，按依赖序执行 |
| 5 | 知识 Agent：MCP+RAG 读实验要求 | 文档解析失败 | PDF 解析容错 + 分段降级 |
| 6 | 代码 Agent：ReAct 循环写代码 | 代码运行是高危工具 | 人机确认（interrupt） |
| 7 | 用户同意后沙箱仿真 | 代码报错 | 报错信息回填，代码 Agent 自我修正（Self-Correction） |
| 8 | 自动防循环控制迭代次数 | 无限迭代 | 每个子 Agent 内部 ReAct 同样受四层防死循环约束 |
| 9 | 写作 Agent 汇总生成报告 | 报告与代码不一致 | 从全局 State 汇总中间结果，而非重新生成 |
| 10 | 评审 Agent 审查 Bug/格式 | 评审遗漏 | 评审 + 自查双重校验 |
| 11 | 子任务失败 → 局部重规划 | 全局重来浪费时间 | 只重规划失败部分，保留成功子任务结果 |
| 12 | 全部完成，沉淀经验 | — | 长期记忆向量库 |

**模式特点**：顶层全局规划、下层多 Agent 分工、每个子 Agent 内部都是 ReAct、自带失败重规划、高危操作用户授权、全程防死循环。

---

### 场景三：主观评审任务 → 多 Agent 对等辩论模式（独立核心场景）

**适用**：课程论文评审、作业批改、主观题打分、逻辑漏洞检测、观点纠错

**案例**：用户上传课程论文，要求"找出逻辑漏洞、论证缺陷、给出修改建议"

**重点**：此场景**完全不使用 Plan-and-Execute**，无预先规划步骤。

| 步骤 | 执行逻辑 | 可能的问题 | 设计的技术 |
|---|---|---|---|
| 1 | 路由分类为 debate | 误判 | 分类器双保险 |
| 2 | 进入辩论子图（无规划） | — | — |
| 3 | 启动三个对等 Agent：立论 / 批判 / 仲裁 | — | — |
| 4 | 立论 Agent 总结论文优点（RAG 读论文） | 立论空洞 | 必须引用论文原文依据 |
| 5 | 批判 Agent 质疑漏洞 | 无根据乱批 | 批判必须引用 RAG 依据（原文定位） |
| 6 | 多轮博弈，写入消息池 | 辩论偏离主题 | 每轮主题相关性检查 |
| 7 | 观点重复 | 语义相似度去重 | 检测重复观点，跳过 |
| 8 | 收敛判断 | 永不收敛 | 最大辩论轮次 + 收敛条件（观点重复/仲裁判定） |
| 9 | 仲裁 Agent 输出最终评审报告 | token 成本爆炸 | 限制轮次 + 每轮控制上下文长度 |

**核心价值（答辩高分点）**：多智能体协作**不必然依赖规划**，主观创造性任务依靠 Agent 间平等交互、动态涌现结果，是**独立于 Plan 架构的第二类多智能体业务形态**。

---

### 场景四：动态模式切换（项目创新点）

**案例**：
1. 用户第一轮："解释页表"（simple → ReAct）
2. 用户追加："基于页表写模拟代码 + 实验报告"（需求升级）
3. 系统重新分类 → complex → 启动 Plan+多 Agent 流水线

| 步骤 | 执行逻辑 | 可能的问题 | 设计的技术 |
|---|---|---|---|
| 1 | 第一轮 simple 执行完 | — | — |
| 2 | 用户追加复杂需求 | 追加需求未被识别为升级 | 分类器检测"升级关键词" + 用户确认 |
| 3 | 系统重新分类为 complex | 状态迁移丢失上下文 | Checkpointer 持久化 State，切换时复用历史 messages |
| 4 | 切换到 Plan 子图 | 子图状态 schema 不兼容 | 全局统一 schema，子图只读写自己关心的字段 |

**价值**：一套系统、三架构自适应。

## 十一、评估体系（原设计缺失，必须补齐）

"能跑"不等于"能落地"，必须用数字说话：

| 指标 | 测量方式 | 目标 |
|---|---|---|
| 任务分类准确率 | 标注测试集，分类结果 vs 真实类型 | > 90% |
| 答案正确率 | 人工/LLM 评测答案质量 | 量化基准 |
| 单任务平均工具调用轮数 | 统计 tool_history 长度 | 验证防死循环有效（应明显收敛） |
| 单任务平均 token 成本 | 统计每次调用 token | 多 Agent 辩论成本可控 |
| 平均响应延迟 | 端到端计时 | 简单任务 < 5s |

## 附：全文关键结论

1. **架构定位正确**：LangChain 能力封装 + LangGraph 编排调度是 2025 标准分工。
2. **范式表述修正**：从"三大范式严格解耦"改为"1 底座（ReAct）+ 2 编排（Plan / 辩论）"，技术上才站得住。
3. **两大真实亮点**：① 分层范式设计；② 人机在环安全确认（LangGraph 原生 interrupt）。
4. **必须补齐的短板**：评估体系、LLM 层容错、上下文管理、可观测性——否则面试官一问就露怯。
5. **落地策略**：分 8 阶段推进，每阶段可运行、可演示，最后再拼成完整系统。
